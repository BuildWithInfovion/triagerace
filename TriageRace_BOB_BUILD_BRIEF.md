## 1. The product in one paragraph

**TriageRace** turns one bug report into a live race between competing root-cause hypotheses. Each hypothesis is produced by a separate IBM Bob subagent, and each one looks through a different "lens" (boundary logic, numeric precision, input validation, order of operations). Every hypothesis comes with a concrete patch. TriageRace applies each patch to its own isolated copy of the repo and **runs the real failing test**, all in parallel, with the cards shown side by side. The hypothesis whose patch makes the test pass turns green. One click then applies the winning patch, runs the **full test suite**, and shows it all green. A results panel then shows the measured manual-debugging time next to the assisted time.

**Pitch line:** *"When a bug comes in, TriageRace fires four Bob subagents at once, each betting on a different root cause. The real test suite decides who's right, live, then the winning fix is verified against the full suite."*

## 5. The sample repo and the seeded bug

Build `sample_repos/shopcart/` as a small, realistic, self-contained Python package. It needs no dependencies beyond pytest.

### 5.1 `shopcart/pricing.py` (use `Decimal` everywhere)

- `DISCOUNT_THRESHOLD = Decimal("100.00")`, `DISCOUNT_RATE = Decimal("0.10")`
- `subtotal(items: list[LineItem]) -> Decimal` returns the sum of `unit_price * quantity`, quantized to cents.
- `validate_coupon(code: str | None) -> bool`: `None` or empty is valid (it means "no coupon"). A known code from a small dict is valid. Anything else is invalid.
- `apply_discount(amount: Decimal) -> Decimal` gives 10% off when the order qualifies. **This is where the seeded bug lives:**

  ```python
  # Promo policy: "10% off orders of $100.00 or more"
  if amount > DISCOUNT_THRESHOLD:   # SEEDED BUG: should be >=
      amount = amount * (1 - DISCOUNT_RATE)
  return amount.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
  ```
- `apply_tax(amount: Decimal, rate: Decimal) -> Decimal` rounds to cents with ROUND_HALF_UP.
- `order_total(items, coupon=None, tax_rate=Decimal("0")) -> Decimal` validates the coupon (raising `ValueError` if it is invalid), then computes subtotal, then discount, then tax, in that order. **Tax is applied after the discount.**

Also add `shopcart/models.py` (a `LineItem` dataclass with `sku`, `name`, `unit_price: Decimal`, `quantity: int`) and a short `shopcart/README.md`.

### 5.2 Tests (`sample_repos/shopcart/tests/`)

- `test_pricing.py` must have **about 8 passing tests**: subtotal math, no discount at $99.99, discount at $150.00, tax after discount (for example $150 → $135 → with 8% tax → $145.80), coupon validation (valid, None, invalid raises), rounding half-up on cents.
- `test_discounts.py::test_discount_applies_at_exactly_100` is the **one failing test**: 2 × $50.00 items with tax_rate 0 should total `Decimal("90.00")`. With the bug, it returns `100.00`.
- The passing tests must be strong enough that **wrong "fixes" break them or fail to fix the target test**. For example, reordering tax before the discount must break the tax-after-discount test.

**Checks:** running `python -m pytest` inside `sample_repos/shopcart` gives exactly 1 failure (the target test) and everything else passing. Changing `>` to `>=` makes all tests pass.

## 6. Hypothesis JSON schema (the contract between Bob subagents and the app)

Each file lives at `scenarios/<id>/hypotheses/<role>.json`:

```json
{
  "id": "boundary-logic",
  "role": "Boundary & comparison logic",
  "title": "Discount threshold uses > instead of >=",
  "suspected_file": "shopcart/pricing.py",
  "suspected_line": 27,
  "reasoning": "2–4 sentences linking evidence in the bug report to the code.",
  "evidence": ["Cart of exactly 100.00 → discount_applied=false", "120.00 cart gets discount"],
  "confidence": 0.8,
  "patch": [
    {
      "file": "shopcart/pricing.py",
      "find": "    if amount > DISCOUNT_THRESHOLD:",
      "replace": "    if amount >= DISCOUNT_THRESHOLD:"
    }
  ],
  "source": "ibm-bob-subagent",
  "generated_at": "2026-09-26T10:15:00+05:30"
}
```

Patch semantics (keep these strict so they are easy to verify):
- `patch` is a list of search/replace edits. Paths are relative to the scenario's `repo_path`.
- Each `find` must match **exactly once** in the target file (exact text, whitespace included). If it matches zero times or more than once, the hypothesis status becomes `patch_failed` with a clear reason. Do not fuzzy-match.
- Edits are applied in order to a **fresh copy** of the repo, never to `sample_repos/` itself.

Validate every file with a pydantic model when it loads. An invalid file is skipped, the problem is logged, and the API reports it (it must not crash).

## 7. Bob subagent prompts → save to `bob_prompts/subagent_prompts.md`

The human runs these **inside IBM Bob (Agent mode) as 4 parallel subagents**, and records the screen while they run. This is the most important piece of evidence for the judges. Each prompt makes Bob read the bug report (document understanding) and the repo, then write one hypothesis JSON file.

**Shared preamble (put it at the top of every role prompt):**

> You are one of four independent debugging subagents racing to find the root cause of a bug. Read `scenarios/discount-threshold/bug_report.md` and the code in `sample_repos/shopcart/`. **Do not modify any file in `sample_repos/`.** Investigate ONLY through your assigned lens below. Propose the single most plausible root cause *within your lens*, even if you suspect another lens is more likely. The race will decide. Produce a minimal patch as exact search/replace edits where each `find` string appears exactly once in its file. Write your result as JSON matching the schema in Section 6 of `BOB_BUILD_BRIEF.md` to `scenarios/discount-threshold/hypotheses/<your-id>.json`, with `"source": "ibm-bob-subagent"` and the current timestamp. Output nothing else.

**Roles:**
1. `boundary-logic`: **Boundary & comparison logic.** Off-by-one errors, `<` vs `<=`, inclusive/exclusive thresholds, edge values stated in business rules.
2. `numeric-precision`: **Numeric precision & rounding.** Float vs Decimal, quantization, rounding modes, values that look equal but aren't.
3. `input-validation`: **Input & coupon validation.** Validation logic that silently rejects or short-circuits the discount path, default arguments, None handling.
4. `order-of-operations`: **Order of operations & data flow.** Whether discount, tax and subtotal are computed in the right sequence and the right values are passed between functions.

Also add a short "How to run" section at the top of `bob_prompts/subagent_prompts.md` for the human: open Bob in Agent mode, start the 4 subagents in parallel (one per role), start a stopwatch, record the screen, and then export the session through **Views → More Actions → History** into `bob_sessions/`.

The UI must show these with a visible **"DEV PLACEHOLDER"** badge. The loader must ignore `_dev_*` files whenever at least one non-dev hypothesis file exists. ## 8. Backend specification

### 8.1 Database (`backend/app/db.py`, file path from env `TRIAGERACE_DB`, default `./triagerace.db`)

- `runs(id TEXT PK, scenario_id TEXT, bug_report_text TEXT, status TEXT, created_at REAL, race_started_at REAL, race_finished_at REAL, winner_hypothesis_id TEXT, verify_status TEXT, verify_started_at REAL, verify_finished_at REAL, verify_output TEXT)`
- `hypotheses(run_id TEXT, hypothesis_id TEXT, payload_json TEXT, status TEXT, started_at REAL, finished_at REAL, test_output TEXT, PRIMARY KEY(run_id, hypothesis_id))`
- `status` for a hypothesis is one of: `queued → patching → testing → passed | failed | patch_failed | timeout | error`.
- `status` for a run is one of: `created → racing → race_done → verifying → verified | verify_failed`.

### 8.2 API

| Method & path | Purpose |
|---|---|
| `GET /api/health` | `{"ok": true}` |
| `GET /api/scenarios` | List scenarios: id, title, and hypothesis count by source. |
| `GET /api/scenarios/{id}` | Scenario details plus `bug_report` text plus `metrics.json`. |
| `POST /api/runs` | Body `{scenario_id, bug_report_text}`. Creates a run, snapshots the hypotheses, and **starts the race in the background** (asyncio task). Returns `{run_id}`. |
| `GET /api/runs/{run_id}` | Full run state: run fields, every hypothesis (payload + status + timings + last ~60 lines of test output), computed metrics. The frontend polls this. |
| `POST /api/runs/{run_id}/apply` | Only allowed when a winner exists. Applies the winning patch to a fresh copy, runs the **full suite**, and stores the result. Runs in the background. The frontend keeps polling. |

Also add CORS for `http://localhost:5173` in dev only, and serve `frontend/dist` at `/` when that folder exists.

### 8.3 Race engine (`backend/app/race.py`)

For each hypothesis, **concurrently** (`asyncio.gather` + `asyncio.create_subprocess_exec`):
1. Copy `repo_path` to `.race_work/<run_id>/<hypothesis_id>/` using `shutil.copytree`, ignoring `__pycache__` and `.pytest_cache`.
2. Apply the patch edits (Section 6 rules). On failure, set `patch_failed` and stop that hypothesis.
3. Run `sys.executable -m pytest -q -p no:cacheprovider <failing_test>` with `cwd` set to the copy and the scenario timeout. Exit code 0 means `passed`. Any other exit code means `failed`. If the time limit is hit, kill the process and set `timeout`.
4. Record `started_at`/`finished_at` and store the output.

**Winner:** the passed hypothesis with the earliest `finished_at`. If none pass, the run is `race_done` with no winner, and the UI says "No hypothesis fixed the failing test". That is an honest outcome, so show it plainly.

**Verify (`/apply`):** apply the winner's patch to a fresh copy, run `python -m pytest -q -p no:cacheprovider <full_suite>`, and parse the pass/fail counts from pytest's summary line. The result is `verified` only if the exit code is 0.

**Safety and limits:** allow at most 2 concurrent runs server-wide (return 429 beyond that). Delete `.race_work/<run_id>` after verification, or 10 minutes after the race. Never use `shell=True`.

**Baseline check:** before the race starts, run the failing test once against the **unpatched** copy. If it passes, the scenario is broken, and the run fails loudly. This proves to judges that the bug is real. Show its result in the UI as "Baseline: test fails on original code ✗ (as expected)".

### 8.4 Backend tests (`backend/tests/`)

Cover these with pytest: a patch that matches once is applied; zero or multiple matches are rejected; scenario and hypothesis loading and validation; `_dev_*` files are ignored when real ones exist; and an end-to-end race on the real scenario with a known-good and a known-bad hypothesis, where only the good one passes.

## 10. Frontend specification

Design goals: this is shown in a 5-minute demo video, so it must be **legible at 1080p, dark theme, with high contrast**. Motion is used only to show real state changes.

### View 1: Intake
- App title "TriageRace" with the tagline "Four hypotheses. One real test. The fastest truth wins."
- A scenario dropdown, loaded from `/api/scenarios`.
- A large textarea prefilled with the scenario's `bug_report.md`. It is editable, but the text is only stored with the run.
- A panel called "What Bob understood" that lists the hypotheses loaded for this scenario (role + title + source badge), so the viewer sees the document-understanding output before the race starts.
- A big **"Start the race"** button → `POST /api/runs` → switch to the Race view.

### View 2: Race (the centerpiece; most of the demo happens here)
- A baseline strip at the top: "Baseline: failing test fails on original code ✗", with its real result.
- A **2×2 grid of hypothesis cards** (4 columns on wide screens). Each card shows:
  - the role name, hypothesis title, suspected `file:line`, confidence bar, and source badge
  - a collapsible "Reasoning & evidence" section
  - a collapsible diff preview of the patch (render the find/replace as red/green lines)
  - a live status pill: `queued / patching / running test… / PASSED / FAILED / PATCH FAILED / TIMEOUT`
  - a live elapsed timer while it is running, and the final duration when done
- When a card passes, it gets a strong **green glow + a "WINNER" ribbon**. Failed cards dim, and they show the last lines of pytest output in a collapsible monospace box.
- A global race timer is shown. It stops when every card is finished.
- When a winner exists: an **"Apply winning fix & run full suite"** button → `POST /apply` → switch to the Result view.

### View 3: Result
- The winning patch shown as a diff.
- Full suite result, for example "✓ 9 passed, 0 failed", with a collapsible full pytest output.
- A **metrics panel** with two big comparison tiles:
  - **Manual (measured baseline):** `manual_baseline_seconds` from `metrics.json`, formatted as mm:ss, plus steps. If the value is null, show `—` and "not measured yet".
  - **Assisted:** `bob_hypothesis_generation_seconds` (null → `—`) + measured race time + measured verify time = total. Show each part so the sum is traceable.
  - Show a speed-up figure (for example "13× faster") **only when both sides are real numbers.**
- A footer: "Hypotheses generated by 4 parallel IBM Bob subagents · session logs in `bob_sessions/`", plus a link to the GitHub repo (read from the `VITE_REPO_URL` env var).
- A "Run again" button.

Use Tailwind only. No component libraries are needed. Keep all API calls in `api.ts`. Polling stops when the run reaches a final state.
